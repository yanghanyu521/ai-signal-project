# 45 个恶意样本规则与 LLM 静态特征提取全量对比报告

## 一、评估结论

本次使用当前 v0.7 静态分析管线和 `deepseek-v4-flash`，对知识库中的 45 个恶意样本进行了完整隔离复测，并与知识库中保存的历史规则结果逐样本对比。测试覆盖 9 个样本家族；全程只进行静态读取、字符串/源码分析和 Docker 反编译，没有执行样本、访问样本中的网络地址，也没有覆盖正式知识库。

本次评估的核心结论是：

1. **LLM 提升了候选特征覆盖，但尚不能独立替代确定性分析。** 新结果中的工具链记录从 70 条增加到 184 条，Prompt 记录从 73 条增加到 107 条；但增加的工具链和代码观察中存在大量通用组件、IOC、编译器信息和普通恶意行为噪声。
2. **Prompt 提取是当前 LLM 效果最好的字段。** 53 条 LLM Prompt 事实中，保守初筛认为 49 条是合理的 AI Prompt 候选，1 条需要 Base64 规范化，3 条属于明显误提。LLM 对损坏 Python 源码和复杂 Prompt 组成的恢复明显优于简单关键词规则。
3. **AI 工具链与代码观察的语义准确性不足。** 96 条 LLM 工具链事实中仅约 47 条属于 AI 模型、AI SDK/CLI 或 AI 服务端点；78 条代码观察中只有 15 条可直接视为 AI 请求、响应或生成代码流，58 条明显属于普通代码或恶意行为。
4. **证据定位可靠，但可归因事实很少。** 227 条被管线接受的 LLM 事实全部能在静态材料中精确找到，哈希、字符偏移和引用单元全部一致；但只有 14 条达到 `attribution_eligible=true`，占 6.2%。这说明当前系统能有效阻止无原文事实进入结果，但多数候选仍没有调用关系支撑。
5. **二进制与 APK/DEX 的 Docker 恢复链路存在 P0 缺陷。** 7 次 JADX 全部未形成正式反编译材料；8 次 Ghidra 中只有 1 次成功，6 次无材料，1 次超时。日志证明主要原因是 Windows Docker 输入 bind mount 在容器内读取样本时报 `Invalid argument`，并非镜像不存在。
6. **无总 Token 预算带来了明显的成本和吞吐问题。** 45 个样本共发起 121 次模型请求，使用约 665 万 Token，总耗时约 51.5 分钟。个别样本使用 80 万至 158 万 Token，但只得到 0—9 条有效事实。

因此，当前最佳使用方式仍应是：**确定性静态材料和关系图作为证据骨架，LLM 用于候选发现、Prompt 恢复和解释；任何 LLM 结果必须经过本地原文校验、语义过滤和关系资格判断。**

### 3.2 历史规则与新结果数量对比

| 指标 | 历史规则 | 新混合结果 | 精确值差异 |
|---|---:|---:|---:|
| 工具链记录 | 70 | 184 | 新增 89，缺少 4 |

这里的“新增”是精确字符串差异，不等于新增了同样数量的语义特征。例如，旧结果可能保存带 `'content':`、`const PROMPT =` 等源码前缀的片段，新结果保存清洗后的正文；两者会被精确比较计为一条缺失和一条新增。MalTerminal 旧规则还会把 `gpt-3.5-turbo-1106` 粗化为 `gpt-3.5-turbo`，新结果保留精确模型值，这属于精度修正而非模型丢失。

### 3.3 分类标签变化

| 标签变化 | 样本数 |
|---|---:|
| `confirmed → probable` | 8 |
| `confirmed → unknown` | 17 |
| `unknown → unknown` | 20 |

历史规则的 `confirmed` 主要依据字符串或规则命中；v0.7 的 `probable` 要求应用代码角色和静态调用关系，且没有运行时观测。因此标签整体降低不应直接解释为识别能力退化，而是置信语义变严格。

但 17 个 `confirmed → unknown` 仍揭示了重要覆盖缺口：二进制、APK/DEX、JavaScript 或语法损坏的 Python 样本无法稳定建立调用关系。8 个 `probable` 中，只有 7 个存在关系合格的 LLM 事实；另一个 LAMEHUG 样本的 `probable` 完全来自确定性 AST 证据，其 LLM 事实为 0。

## 五、字段效果分析

### 5.1 Prompt 特征

Prompt 是本次表现最好的字段。

- LLM 能从 AST 失败的 LAMEHUG 源码中恢复命令生成 Prompt、图像正向 Prompt 和负向 Prompt。
- 对 QUIETVAULT，LLM 去除了 `const PROMPT =` 等源码包装，输出更适合前端展示和相似性比较。
- 对 MalTerminal，LLM 能识别复杂代码生成指令及多个 Prompt 组成部分。

存在的问题：

1. 精确字符串差异把清洗、转义和空白变化误计为新增，38 条精确新增明显高于真实语义增量。
2. FRUITSHELL 中“不要分析此文件、程序无恶意”的分析器定向注释被当成普通 Prompt；它应进入 `analysis_targeting`，不能进入应用 Prompt。
3. `What should not be on the image` 之类界面标签被当成 Prompt 内容。
4. 至少 1 条 Prompt 仍以 Base64 文本保存，没有输出规范化解码值。
5. 53 条 LLM Prompt 事实均未达到归因资格，说明“找到 Prompt”与“证明 Prompt 被发送给模型”仍是两回事。

保守语义初筛结果：49 条合理 AI Prompt 候选、1 条需规范化、3 条明显误提。该数字是本轮初筛，不是人工金标准准确率。

### 5.2 AI 工具链

工具链是误分类最严重的核心字段。

合理候选包括：

- Qwen/Qwen2.5-Coder-32B-Instruct；
- black-forest-labs/flux-dev；
- OpenAI SDK 和 GPT 模型参数；
- Claude、Gemini、Q CLI 候选；
- HuggingFace Router 下明确的对话和图像生成端点。

明显噪声包括：

- 普通网络/远程访问库：`requests`、`paramiko`、`System.Net.WebClient`；
- 图像或文档库：PIL、Aspose；
- 键盘记录、混淆和打包组件：pynput、PyArmor、Nuitka、joblib；
- 编译/运行组件：LLD、clang、JNI/VNC；
- IOC 或普通端点：IP、webhook、GitHub API、C2 地址；
- 仅出现在 HTTP 头或字符串中的组件名。

按“AI模型、AI SDK/CLI、AI服务端点”口径，96 条工具链事实中约 47 条合理、49 条属于非 AI 或错误归类，初筛语义精确率约 49%。这些噪声多数因没有关系资格而未改变最终分类，但会污染前端展示、知识库相似度和人工研判。

### 5.3 代码生成/代码观察

78 条代码观察中，合理的 AI 流程证据主要是：

- 模型请求中的 messages/prompt 绑定；
- OpenAI 风格响应内容读取；
- `llm_query` 调用；
- 图像生成请求和响应；
- 将模型返回内容写入文件或交给 `exec` 的路径。

明显无关项包括 Nuitka 内部字符串、JNI 函数、VNC 方法、AndroidX 符号、键盘记录、hosts 修改、持久化命令、普通文件写入、C2 命令和关机命令等。

保守初筛为：15 条 AI 相关候选、5 条需结合关系人工复核、58 条明显非 AI。说明当前 Prompt 设计对 `code_observation` 的边界过宽，模型容易把“样本中任何值得注意的代码”都输出到该字段。

### 5.4 证据验证与事实拒绝

模型共产生至少 420 条候选事实：

- 227 条通过本地证据验证并进入结果；
- 193 条被拒绝；
- 接受率约 54.0%。

被拒绝事实中：

- 159 条为 `toolchain_fact_has_no_typed_identity`，说明模型返回的工具链候选缺少 Schema 要求的模型、SDK 或端点类型；
- 34 条为 `raw_value_not_in_material`，说明返回文本无法与静态材料逐字回绑，可能是改写、转义变化、截断或生成错误。

正面结果是：进入最终结果的 227 条事实全部通过原文、哈希、偏移和引用单元核验，没有发现无原文依据的事实。当前本地证据门禁有效，不能移除。

## 六、主要问题分级

### P0：应优先解决

#### P0-1 Docker 输入传输导致二进制/DEX材料恢复大面积失效

本次工具运行情况：

- JADX：7 次运行均未形成正式反编译材料；
- Ghidra：1 次成功、6 次无材料、1 次超时。

失败日志显示，容器内打开 `/input/sample.apk` 或 `/input/sample.bin` 时出现 `FileNotFoundException (... Invalid argument)`。工具进程部分情况下仍返回 0，适配器误判为运行成功，再以 `no_decompiler_material` 结束。

已做独立静态冒烟验证：使用命名卷暂存输入后，以只读方式挂载给分析容器，JADX 可以完整读取同一样本并处理 3,887 个对象。这证明镜像本身可用，问题在 Windows Docker bind mount 输入方式。

整改建议：

1. Windows 使用“无网络暂存容器 + `docker cp` + 命名卷只读挂载”的输入方式；Linux 保留目录 bind mount。
2. 解析容器日志中的输入读取错误，不能只相信 exit code。
3. 工具非零退出但已生成反编译文件时，应标记 `partial` 并读取可用材料，而不是全部丢弃。
4. 修复后单独建立新评估版本，重跑 15 个 Docker 样本，不能覆盖本批次快照。

#### P0-2 AI字段语义边界过宽

工具链中约一半是普通 SDK、IOC 或构建组件；代码观察中约四分之三明显与 AI 代码生成无关。必须在模型输出契约和本地后处理同时限制：

- AI 工具链只允许模型、AI SDK/CLI、AI 服务端点、明确模型参数；
- 普通依赖移入“依赖组件”；
- IP、域名、webhook 移入 IOC；
- 持久化、键盘记录、远控、文件加密等移入“行为特征”；
- 编译器、打包器、运行时移入“构建/运行环境”；
- `code_observation` 只接受能说明 AI 请求、响应、Prompt 组装、生成内容落盘或执行的代码关系。

#### P0-3 高成本低产出且缺少有效早停

用户配置要求不设置总 Token 预算，本次实际出现：

- `dc9f…`：158 万 Token、24 次请求、23 条事实；
- PROMPTFLUX：80 万 Token、9 次请求、1 条事实；
- PromptSpy `db7a…`：80 万 Token、12 次请求、9 条事实；
- PromptSpy `11f5…`：70 万 Token、11 次请求、9 条事实；
- PromptSpy `299a…`：31 万 Token、5 次请求、0 条事实。

整改不一定要恢复固定总 Token 上限，但应增加材料质量和收益驱动的早停：

- 没有 AI 锚点且连续批次无有效事实时停止；
- 优先发送调用点、模型参数、Prompt 相关字符串和引用邻域；
- 对大量反编译单元先本地聚类/去重，再由模型请求上下文；
- 单独记录“每条被接受事实的请求数和 Token”；
- 高成本样本需要人工确认后再继续扩展上下文。

### P1：影响准确性与可复现性

#### P1-1 请求成功不等于提取成功

13 个样本没有任何 LLM 事实，其中：

- 3 个为 `unsupported`；
- 1 个为 `partial`；
- 其余样本完成模型请求但没有事实通过验证。

PromptLock 三个样本共消耗约 44.7 万 Token，LLM 事实仍为 0。需要在前端和 API 中分别显示“未调用模型、模型调用失败、模型返回为空、候选全部被拒绝、确实没有 AI 特征”。

#### P1-2 两个旧 Prompt 明确退化样本

LAMEHUG：

- `bdb33bbb4ea1…`
- `d6af1c9f5ce4…`

历史规则各有 2 条 Prompt，新结果 Prompt 为 0。两者均发生 Ghidra 输入恢复失败，说明二进制恢复问题已经造成真实字段丢失，而不是标签标准变化。

#### P1-3 Prompt规范化和语义去重不足

精确差异把源码包装、转义、空白和清洗后的同一 Prompt 计为不同值。应形成统一规范化值：

- 去除字典键、赋值语句和引号包装；
- 规范转义和空白；
- 保留原文、规范化正文和变换说明；
- Base64 等可验证编码同时保存原文和解码值；
- 相似性和统计默认按规范化正文去重。

#### P1-4 模型运行间存在波动

同一 MalTerminal `4c73717d933f…` 在 9 月 18 日相同模型复测中得到 8 条 LLM 事实，本批次得到 10 条。即使温度为 0，推理模型、服务端实现和结构化输出仍可能产生波动。

重要评估样本至少应重复运行 2—3 次，分别报告稳定事实、偶发事实和差异；不能用单次事实数量作为模型版本优劣结论。

### P2：需要持续完善

- JavaScript/PowerShell 目前只有词法材料，缺少调用、参数和数据流关系；QUIETVAULT、FRUITSHELL 的候选无法晋级。
- 模型/厂商归一化不完整，例如 `q` 只能作为 CLI 候选，不能直接确定模型厂商或版本。
- 1 个样本出现 LLM JSON 字符串截断，当前降级为 `partial`，但需要记录原始响应长度、截断位置和是否可做安全修复。
- 运行覆盖率与业务效果需要同时展示；`completed` 不能直接表示“找到特征”，`unknown` 也不能直接表示“样本不使用 AI”。

## 七、后续建议与验收顺序

1. 先修复 Windows Docker 输入和部分产物读取，重跑受影响的 15 个样本。
2. 收紧工具链和代码观察 Schema，并把普通依赖、IOC、行为、构建信息分流到独立字段。
3. 对 Prompt 建立规范化、解码和语义去重，再重新计算规则—LLM增量。
4. 为 Python 语法错误增加分段/容错解析，为 JavaScript、PowerShell 增加调用与参数关系。
5. 增加连续无收益早停、材料优先级和每条事实成本指标；即使不限制总 Token，也要避免无差别遍历全部反编译材料。
6. 从 45 个样本中建立人工标注集，至少逐条标注工具链、Prompt、代码观察、是否可归因；之后再报告正式 precision/recall。
7. 对代表性样本重复运行，评估模型结果稳定性。

建议的阶段验收标准：

- Docker 样本可读取率 100%，非零退出的部分材料可保留；
- AI 工具链初筛精确率不低于 90%；
- `code_observation` 非 AI 噪声低于 10%；
- Prompt 原文、规范化值和编码变换均可追溯；
- 所有用于归因的事实必须具备原文、位置、应用角色和调用关系；
- 高成本无事实样本能够触发可解释早停。

## 八、输出结果管理

## 九、最终判断

全量结果证明 LLM 对 Prompt 发现和复杂源码理解具有现实价值，尤其适合补充规则未覆盖的表达方式；同时也证明“把更多静态材料直接交给 LLM”不会自动得到更可靠的 AI 特征。当前主要矛盾已经从“能否找到文本”转变为：

- 静态材料能否可靠恢复；
- 候选是否真正属于 AI 字段；
- 是否有调用关系可以用于归因；
- 额外覆盖是否值得请求和 Token 成本。

因此，目前不建议用 LLM 结果直接替代规则或直接写入高置信知识库。应先完成 Docker 恢复、语义分流、Prompt 规范化和成本早停，再基于人工标注集评估正式准确率。现有的原文验证和归因资格门禁有效，应继续保留。
