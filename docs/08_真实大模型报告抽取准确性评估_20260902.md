# 真实大模型报告抽取准确性评估

日期：2026-09-02。评估版本：统一平台 0.3.0。结论：**模型调用可用，但当前抽取准确性尚不足以支持无人复核的可信入库。**

## 1. 本次实际做了什么

- 已确认原有 `cc-api` 存在于当前进程和用户环境。使用该密钥请求官方模型列表，返回 HTTP 200；未打印或落盘密钥。
- 调用真实 `deepseek-v4-flash`，使用现有生产代码、现有提示词、temperature=0、非思考模式、max_tokens=8192；没有用模拟响应代替。
- 首轮分析 9 个家族—报告组合；包含 GTIG 同一文章用于不同家族的情况，并非 9 篇相互独立文章。
- 保持参数不变复跑 FRUITSHELL、PROMPTSTEAL、PROMPTFLUX、MalTerminal 共 4 个目标。
- 增加 1 个不存在目标的负对照：在 PromptLock 报告中提取 `EVAL_NONEXISTENT_FAMILY_9B7C`。
- 共 14 次报告评估、16 次模型生成 HTTP 请求（含输出截断后的子请求）；另有 1 次只读模型列表请求。提供商返回用量合计：输入 180,058 tokens、输出 38,526 tokens，其中输入缓存命中 96,256 tokens。这里不把用量换算成未经账单核对的费用。
- 只处理用户已有报告及其解析文本，不运行/上传恶意样本文件，不写入正式知识库，不修改生产提取逻辑、提示词或用户模型配置。

完整产物位于项目 `data/evaluations/20260902_llm_accuracy/`：

- `source_manifest.json`：源文件路径、哈希、解析规模。
- `sources/<家族>/parsed_text.txt`：按段落编号保存的模型输入文本；编号从 0 开始。
- `baseline/`：首轮候选、成功结果、失败原因及请求审计。
- `repeat/`：四个目标的同参数复跑。
- `negative_control/`：不存在目标测试。

复现脚本：`scripts/evaluate_report_accuracy.py`。重跑使用新的 `--batch` 名称，避免覆盖已有结果；会产生真实模型调用费用。

## 2. 怎么理解指标

| 指标 | 实测 | 含义 |
|---|---:|---|
| 首轮结构与证据校验通过 | 7/9（77.8%） | 能返回可交付结构的比例，**不是字段准确率** |
| 首轮被拒绝 | 2/9 | MalTerminal、PROMPTFLUX，没有成功结果 |
| 四目标同参数复跑 | 2 成功、2 失败 | 两个成功目标的关键错误/遗漏再次出现；两份失败原因重现 |
| 不存在目标的负对照 | 1/1 正确拒绝 | 模型返回 event=null，未构造该目标 |

本轮由助手逐项对照原文审核成功结果的所有字段组，并对失败候选作诊断。旧规则结果、静态样本结果和模型自评均没有被当作标准答案。

这不是独立双人标注、盲测或完整金标准基准：没有对每个可抽取原子事实完成穷尽标注，也没有估计置信区间，因此**不能据此宣布整体准确率、精确率或召回率为某个百分比**。七份程序通过的结果中，均发现需修正的语义、遗漏或字段契约问题，严重程度不同。

## 3. 各家族结果

| 目标 | 首轮交付 | 提取得较好的内容 | 主要问题 |
|---|---|---|---|
| FRUITSHELL | 通过 | PowerShell、反向 Shell、C2 任意命令、实际行动中观察到 | 明确存在硬编码反分析 Prompt，但 `ai_signals.prompts=[]`、AI 参与字段为空；只写到了行为描述 |
| LAMEHUG | 通过 | Qwen 2.5-Coder-32B-Instruct、Hugging Face API、Python/PyInstaller、信息与文档收集、SFTP/HTTP POST | 归因类型/置信度补全、自治级别推断；模型厂商与服务商字段混用 |
| MalTerminal | 拒绝 | 原始候选识别 GPT-4、代码生成、Python、未见部署证据；15 个 SHA-256 本身均在正文 | 哈希引用的证据不包含哈希；候选把明确标注为防御工具的文件并入恶意文件集合 |
| PROMPTFLUX | 拒绝 | 原始候选涉及 Gemini、VBScript、自修改用途 | 全文输出先触发 8192 上限，分块后摘录空格变化导致拒绝；不能交付完整结果 |
| PromptLock | 通过 | OpenAI/gpt-oss-20b、本地 Ollama、Lua、Go、Windows/Linux、未见实际攻击/销毁未实现 | 将生成代码推断成 `code_only=true`；Ollama 被放进 Agent/协议字段而不是 service；自治与执行审查情况缺少充分依据 |
| PromptSpy | 通过 | Google Gemini、Android、持久化/UI 操作、VNC、辅助功能滥用、AES 通信 | 把“可能为 PoC”“似乎主要针对阿根廷”填成确定状态；Gemini 填入具体版本字段但 family 为空；未给依据却填归因置信度 |
| PROMPTSTEAL | 通过 | Qwen2.5-Coder-32B-Instruct、Hugging Face、Python/PyInstaller、APT28/FROZENLAKE、LAMEHUG 别名、乌克兰、盲执行 | **串入 PROMPTFLUX 的否定结论**；厂商/托管商混用；部分 Prompt 细节仅引用图注 |
| QUIETVAULT | 通过 | JavaScript、主机 AI CLI、GitHub/npm 令牌、公开仓库外传；未编造具体模型 | 将凭证当作受害实体；把令牌窃取标成 initial_access；部分缺失信息被写成带证据的报告声明 |

“提取得较好”只表示这些被列举内容能在报告中找到支持，不代表整条记录全部正确，也不代表每个家族下所有样本都具有这些特征。当前评估是家族—报告层面，不是 45 个具体 SHA-256 的逐样本事实核验。

## 4. 关键问题的可复核证据

下文源段落编号对应 `sources/<家族>/parsed_text.txt`；字段路径从目标 `events[0]` 起算。被拒绝案例的字段来自 `llm_response_1.json` 的 `event`，不把它们算作成功结果。

### A. 严重：跨家族否定结论串入

- 目标：PROMPTSTEAL。
- 输出路径：`limitations[0]`。
- 输出：`The current state of this malware does not demonstrate an ability to compromise a victim network or device.`
- 引用证据：`evidence:27d043744c6df6c3b875`；完整摘录第一句明确说的是 `Further examination of PROMPTFLUX samples ...`，所在章节也是 PROMPTFLUX 章节。
- 源段落 86 属于 PROMPTFLUX；段落 95 则明确 PROMPTSTEAL 已在真实行动中使用。
- 同参数复跑再次出现同一错误。

结论：逐字证据存在、字段结构合法、目标名称正确，仍不能证明该证据属于该目标。`target_event_only=true` 目前仅说明输出只有目标事件，**不是语义归属已验证的保证**。

### B. 严重：已识别的信息没有进入对应特征字段

- 目标：FRUITSHELL；源段落 59/66 明确写有硬编码 Prompt，用于绕过 LLM 安全系统的检测或分析。
- 输出 `key_behaviors[1]` 已描述该事实，但 `ai_signals.prompts` 为空，`ai_involvement.roles` 也为空。
- 正确处理至少应产生一个 `availability=described_only`、`text=null` 的 Prompt 用途记录；不能因为没有完整 Prompt 原文就把整个 Prompt 特征视为不存在。
- 同参数复跑仍缺失。

影响：用户只调用 Prompt 特征字段或做样本—报告交叉验证时，会漏掉已经在同一 JSON 的行为字段中出现的证据。

### C. 严重：推测与确定状态并存

- 目标：PromptSpy；源段落 2：“似乎以盈利为目的”“主要针对阿根廷用户”“遥测数据中尚未发现”“可能表明……概念验证阶段”。
- 输出 `status.value=proof_of_concept`；`targets[0].status=targeted`、地区 Argentina。
- 同一结果的 `limitations` 又正确保留了推测和未被遥测观察到的限定。

结论：不是完全没理解原文，而是 Schema 中的主字段无法表达判断强度，模型把限定留在另一处。只读取主字段的 API 调用方会收到比原文更确定的结论。

### D. 明显误推断：生成代码不等于“只输出代码”

- 目标：PromptLock；源段落 9 说明模型动态生成 Lua 脚本并执行，没有给出“只输出代码”约束。
- 输出 `ai_signals.prompts[0].structural_features.code_only=true`。
- `code_only` 在现有数据字典中的含义是是否要求仅输出代码，不是是否生成过代码。

影响：此类错误可能在交叉验证中制造虚假的 Prompt 结构匹配。`unattended`、`blindly_executed` 等字段同样不应仅由“之后执行了生成代码”直接升级得出。

### E. 厂商、托管服务与协议字段混用

- LAMEHUG 源段落 41、PROMPTSTEAL 源段落 78/95：Qwen 模型通过 Hugging Face 服务 API 调用。
- 输出分别把 `huggingface.co/Hugging Face` 填进 `provider`；现有数据字典/比较器把该字段用于模型或工具厂商匹配。
- PromptLock 则 `service=null`，将 `Ollama API` 填在 `agent_or_protocol`。
- PromptSpy 仅给 Gemini 家族名称，输出却为 `model=Gemini`、`family=null`。

这是字段语义与规范化问题，不能靠“文本里出现了这个词”解决。报告没有给出的模型厂商也不能凭常识强填；应分离模型开发方、托管服务、SDK、协议，并对“仅有家族、没有版本”作清晰表达。

### F. 不能把提取器估计当成作者置信度

- LAMEHUG 的来源只是“有一定程度的置信度”，模型填 `confidence=medium`，并补 `actor_type=state_sponsored`，后者在本报告的归因句中未明确表述。
- PROMPTSTEAL 与 SLOPOLY 输出作者 `confidence=high`，原文没有相应 high-confidence 表述。
- 现有字段字典定义该值是报告作者的置信度，不是提取器自己的概率。

建议作者置信度未明确时填 `not_stated`，另设提取器置信度与断言状态，避免混为一谈。

### G. SLOPOLY：否定能力漏抽、时间精度风险

- 源段落 21 明确不能在执行时修改自身代码，并指出未使用的 Jitter 函数；输出没有保留这两点。
- 输出保留了 “Polymorphic C2 Persistence Client” 注释，却漏掉否定其多态/自修改能力的解释，容易形成偏差。
- 源段落 9 是 `In early 2026`；输出 `time.start=2026-01-01`、`precision=year`。
- 仓储 `_event_date` 取 `time.start`，月份统计用日期前 7 个字符，不结合精度。如果此结果入库，会被归进 2026-01。本轮隔离评估没有实际入库。

应保留年级表达或日期区间，不把未知月份固定到 1 月；不能把标准化占位日期当作实际发生日。

### H. MalTerminal：哈希正确，但证据绑定与文件角色错误

- 源段落 81 中 15 个 MalTerminal SHA-256 与候选输出的哈希相同，未发现这些哈希被捏造。
- 但 `artifacts[0].evidence_ids` 指向身份/介绍/文件表说明，没有引用包含哈希的证据，导致整份报告拒绝。
- 源段落 64/65 明确 `TestMal3.py` 与 `Defe.py` 是防御工具 FalconShield；候选却把它们与恶意文件一起放入 `role=恶意软件` 的单一集合。
- 同参数复跑仍在哈希证据校验处失败。

应区分“值错误”和“证据绑定错误”，以及同一研究中关联工具与真正恶意样本的范围。

### I. PROMPTFLUX：排版差异触发失败，不应统称幻觉

- 第一请求输入 16,357 tokens，输出到 8,192 tokens 被截断；随后触发分块。
- 源段落 87 中模型标识的引号内有空格：`" gemini-1.5-flash-latest "`、`" -latest "`。
- 模型证据 e8/e11 去掉了引号内空格，当前精确子串校验因此失败。
- 同参数复跑再次失败。

此处主要是证据排版/定位可靠性问题。适当的可审计空白归一或原文区间定位可解决一部分，但不应允许模型任意改写原文，也不应放宽到接受跨家族错误证据。

### J. QUIETVAULT：受害对象与窃取数据混淆

- 源段落 3/5 讲窃取 GitHub/npm 令牌。
- 输出把 `GitHub tokens`、`npm tokens` 填进表示受害实体的 `targets`；它们实际是被收集的凭证类型，不是受害组织或地区。
- `key_behaviors[0].stage=initial_access` 也没有来源支持，原文描述的是凭证访问/收集。

## 5. 为什么现有 32 项自动化测试没发现这些问题

之前的测试使用模拟模型输出，验证的是接口、数据流、默认模式、拒绝无效证据及保存行为，不是现实模型的语义质量。

本轮发现：

1. 结构校验能检出缺字段和类型错误，不能判定字段含义是否正确。
2. 引用校验能验证摘录存在，不能判断主体归属和限定条件是否一致。
3. 对象级证据过粗，一个摘录可能只支持该对象部分属性。
4. 纯 JSON Schema 只描述字段类型，未充分传达数据字典中的业务含义。
5. 当前 schema 对大部分字段缺乏逐项 `assertion_status`，会促使模型把“可能”挤进确定枚举，再把限定写到 limitations。
6. 模型是否读过全部正文，与是否将所有事实放入正确特征字段，是两件不同的事。
7. 部分报告的 Prompt/代码在图片中。当前只有解析文本、没有新增 OCR/视觉输入，不能评估成“已阅读所有图片内容”。

## 6. 建议的修改优先级（本轮未实施）

不需要恢复基于关键词的报告规则预筛选；继续保持大模型提取，但补上质量控制。

**第一优先级：阻止错误事实进入可信字段。**

- 引入逐字段/逐声明的 `assertion_status`：明确陈述、作者判断、可能、否定、未报告；区分作者置信度和提取器置信度。
- 增加独立的模型复核步骤，针对候选值检查目标归属、证据是否支持全部属性、限定条件是否保留。复核看到原文及邻接语境，不只看候选摘要；无法确认则拒绝或待复核。第二次模型判断仍需金标准检验，不能当作自动真理。
- 主字段与 limitations 一致性检查：同一对象不能一边填确定 PoC/确定目标，一边写仅为推测；跨家族结论必须拒绝。

**第二优先级：补齐字段与证据。**

- 给模型提供字段含义和正反例，明确模型厂商/服务商、模型家族/版本、Prompt code_only、受害实体/被盗数据的区别。
- 增加完整性复核：报告已识别到的 Prompt 用途必须进入 Prompt 专门字段；否定能力不能被正向代码注释掩盖。
- 以原文位置/区间绑定证据；仅对空白等可逆排版差异做可审计修复，不任意放宽内容匹配。
- 长输出优先在实际模型允许范围增加输出预算或按字段分次提取，再考虑切断正文，避免输出超限损伤跨段语境。

**第三优先级：正式准确性验收。**

- 人工标注一份逐字段金标准，保留原文位置、目标范围和断言状态；旧规则结果只能做对照，不能做真值。
- 分开统计：字段精确率、字段召回率、主体归属错误率、断言状态正确率、证据有效率、交付失败率。
- 修复后重测本批，并加未参与提示词调优的报告；重复运行检验稳定性。不能只在同一批错误样例上反复调优后宣称泛化准确率。

本轮只完成真实验证和诊断。所有评估产物与正式知识库隔离，未直接修改生产抽取器，也没有将发现的问题自动“修正后再报喜”。
