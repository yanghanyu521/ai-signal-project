# 三家族恶意样本规则与 LLM 静态特征提取对比

## 一、结论

本次从既有 45 个样本中选择了 MalTerminal、LAMEHUG、QUIETVAULT 三个不同家族的样本。三个样本的历史规则结果均已提取出 AI 工具链和 Prompt 特征。本次在不执行样本、不覆盖知识库的前提下，分别生成三份结果：历史规则结果、v0.7 确定性静态分析结果、v0.7 确定性分析加 DeepSeek 的完整结果。

总体结论如下：

1. **LLM 对“规则或语法分析覆盖不到的文本”有明显补充价值。** LAMEHUG 因源码存在语法错误，AST 解析失败；LLM 仍从原始源码中恢复出完整 Prompt、遗漏的 Flux 模型和 AI 服务端点。QUIETVAULT 当前只有词法级 JavaScript 材料，LLM 能识别 Claude、Gemini、Q 三个 CLI 候选并清洗出纯 Prompt 正文。
2. **LLM 对结构化分析已经完整的样本增益很小。** MalTerminal 的 4 条 Prompt、OpenAI 调用关系和精确模型参数均已由 v0.7 Python AST 分析恢复；LLM 没有增加新的唯一工具链或 Prompt，只重复确认既有事实并补充 4 条代码流程观察。
3. **LLM 的原文定位可靠，但字段语义仍会误判。** 27 条 LLM 事实的引用单元、原文、SHA-256 和字符偏移全部核验一致，未发现凭空生成的证据；但 LLM 将 webhook、普通 IP、`requests`、`paramiko`、GitHub API、HTTP 头中的 `axios/1.4.0` 等普通网络或组件信息误放入 AI 工具链。
4. **新管线的严格门禁是必要的。** MalTerminal 有 2 条 LLM 工具链事实通过调用关系核验；LAMEHUG 和 QUIETVAULT 的 LLM 新增项均只有位置核验，没有调用关系核验，因此没有直接参与最终归因。旧规则把三个样本都标为 `confirmed`，但旧结果没有角色、调用关系和归因资格字段，这种“确认”明显偏宽，不能与新标签直接等价比较。
5. **当前最合适的路线仍是“确定性静态分析为骨架，LLM 用于补充和解释”。** 现阶段不适合完全用 LLM 替代规则、AST 或反编译关系分析。

## 二、测试对象与方法

| 家族 | 样本 SHA-256 前缀 | 格式 | 选择原因 |
|---|---|---|---|
| MalTerminal | `4c73717d933f` | Python | 历史规则已提取 OpenAI 工具链和 4 条 Prompt，可验证 LLM 在结构完整样本上的增量 |
| LAMEHUG | `384e8f3d3002` | Python（存在语法错误） | 历史规则已提取 Qwen 和 2 条 Prompt，可验证 LLM 对 AST 失败样本的补充能力 |
| QUIETVAULT | `8eea1f65e468` | JavaScript | 历史规则已提取 Claude CLI 和 1 条 Prompt，可验证 LLM 对非 Python 源码的补充能力 |

测试采用当前项目配置的 `deepseek-v4-flash`，每个样本调用 1 次，传输策略为 `remote_redacted`，不设总 Token 预算。三个样本均完成分析，无请求错误；仅进行静态读取，没有执行样本、访问样本内网络地址或写回正式知识库。

对比时没有只比较“条数”，而是同时核对以下内容：

- 工具链和模型是否真实存在、是否属于 AI 工具链；
- Prompt 是否为完整正文，还是带有源码语法前缀的字符串片段；
- 新增项是否真正增加语义信息，还是对旧结果的重复或清洗；
- 证据原文、哈希、字符偏移和引用材料是否一致；
- 是否建立了“Prompt/模型—调用点—应用代码”的静态关系，能否参与归因。

## 三、逐样本对比

### 3.1 MalTerminal

| 对比项 | 历史规则 | v0.7 确定性分析 | v0.7 + LLM |
|---|---|---|---|
| AI 工具链 | OpenAI、`gpt-3.5-turbo`；存在重复字符串记录 | 通过 AST 识别 `openai.ChatCompletion.create` 和精确参数 `gpt-3.5-turbo-1106` | 重复确认 OpenAI 和精确模型，没有新增唯一工具链 |
| Prompt | 4 条 | 4 条，均绑定到静态调用关系 | 仍为相同 4 条；LLM 事实中重复提到其中 2 条 |
| 结构信息 | 无调用关系和角色字段 | 形成 1 个 Prompt 组合，工具链和 Prompt 均有应用代码关系 | 补充消息构造、响应内容读取、`exec` 等 4 条代码观察 |
| 最终标签 | `confirmed` | `probable` | `probable` |

效果判断：**LLM 增量较低。** 真正的提升主要来自新的 Python AST 确定性分析，而不是 LLM。历史规则把实际的 `gpt-3.5-turbo-1106` 粗化为 `gpt-3.5-turbo`；v0.7 修正了模型精度，并用调用关系证明其位于应用代码中。新标签为 `probable` 是因为目前只有静态调用关系，没有运行时观测，不代表识别能力下降。

### 3.2 LAMEHUG

LAMEHUG 在第 324 行存在语法错误，当前 Python AST 无法建立函数和调用关系。因此，它最能体现 LLM 的补充价值和限制。

| 对比项 | 历史规则 | v0.7 确定性分析 | v0.7 + LLM |
|---|---|---|---|
| AI 模型 | Qwen2.5-Coder-32B-Instruct | 保留 Qwen 字符串，但只能作为位置标记 | 补出 `black-forest-labs/flux-dev`，并识别 Qwen 完整选择器 |
| AI 服务 | 未提取 | 未提取 | 补出 HuggingFace Router 下的 Hyperbolic 对话端点和 Nebius 图像生成端点 |
| Prompt | 2 条，正文前带有源码字典语法片段 | 仍为 2 条字符串片段 | 清洗出上述 2 条完整正文，并新增 1 条图像正向 Prompt 和 1 条负向 Prompt；语义唯一 Prompt 从 2 条增加到 4 条 |
| 噪声 | 无明显新增噪声 | 无 | webhook、普通 IP、`requests`、`paramiko` 被误列为 AI 工具链 |
| 最终标签 | `confirmed` | `unknown` | `unknown` |

效果判断：**覆盖提升明显，归因能力尚未提升。** LLM 找到了规则遗漏的 Flux 模型、两个 AI 服务端点和两条新 Prompt，是本次三组中收益最高的样本；但由于源码语法错误导致关系图缺失，这些新增项全部只有位置核验，不能证明它们确实进入了运行时 AI 调用。严格门禁将最终标签保持为 `unknown` 是合理的。

### 3.3 QUIETVAULT

| 对比项 | 历史规则 | v0.7 确定性分析 | v0.7 + LLM |
|---|---|---|---|
| AI 工具链 | Claude CLI 片段 | 保留 Claude CLI 位置标记 | 识别 Claude、Gemini、Q 三个 CLI/模型候选；Gemini 和 Q 为真实新增候选 |
| Prompt | 1 条，带 `const PROMPT =` 源码前缀 | 仍为词法字符串 | 提取出不带源码前缀的纯 Prompt 正文；没有新增第二条语义 Prompt |
| 噪声 | 无明显新增噪声 | 无 | GitHub API、仅位于 HTTP 头中的 `axios/1.4.0` 被误列为 AI 工具链；关机命令被列为代码观察 |
| 最终标签 | `confirmed` | `unknown` | `unknown` |

效果判断：**实体覆盖有提升，关系验证不足。** LLM 能理解 JavaScript 对象中的多个 CLI 选项，明显优于单条 Claude 规则；但当前 JavaScript 分析只提供词法材料，没有形成调用/参数关系，所以新增候选不能直接参与归因。Prompt 的变化主要是清洗，不应被统计为新增 Prompt。

## 四、量化结果与准确性判断

### 4.1 证据可靠性

| 指标 | 结果 |
|---|---:|
| LLM 返回的结构化事实 | 27 条 |
| 引用材料存在 | 27/27 |
| 原文能在引用材料中精确找到 | 27/27 |
| 原文 SHA-256 匹配 | 27/27 |
| 字符偏移匹配 | 27/27 |
| 达到归因资格 | 2/27，均来自 MalTerminal |
| 仍需语义复核 | 27/27 |

这说明当前“模型输出后再做本地证据校验”的机制有效阻止了无原文依据的事实进入结果，但它只能保证“文本确实存在”，不能自动保证“文本被分到了正确的业务字段”。

### 4.2 AI 字段语义准确性

将 LLM 输出中的工具链和 Prompt 作为核心 AI 字段进行人工复核：

- 核心 AI 字段候选共 22 条；
- 其中 16 条属于合理的 AI 工具链、模型、AI 服务端点或 Prompt；
- 6 条属于普通 webhook/IP/网络库/通用 API 等错误归类；
- 本组三样本上的人工复核语义精确率为 **16/22，约 72.7%**。

该比例只反映本次三个样本，不能作为项目整体准确率。更重要的是，现有归因门禁没有让这 6 条噪声直接改变最终标签，因此当前主要风险是前端候选信息偏杂，而不是错误候选自动变成高置信结论。

### 4.3 真正的增量

- Prompt：历史规则共得到 7 条语义唯一 Prompt；新结果共得到 9 条，真实新增 2 条，均来自 LAMEHUG。其余“新增”主要是去掉源码语法前缀后的规范化正文。
- 模型/CLI：真实新增 Flux、Gemini、Q 三类候选；MalTerminal 的变化是把模型从粗粒度 `gpt-3.5-turbo` 修正为源码中的精确值 `gpt-3.5-turbo-1106`。
- 调用关系：只有 MalTerminal 建立了可靠关系，而且这一能力来自 AST；LAMEHUG 和 QUIETVAULT 的 LLM 新增项仍是候选，未形成可归因的结构关系。

## 五、后续改进建议

1. **增加 LLM 输出字段的语义过滤。** `toolchain` 只接收 AI 模型、AI SDK/CLI、AI 服务端点和明确的模型参数；普通 IOC、网络库和恶意行为应分别进入 IOC、依赖组件或行为字段，不得混入 AI 工具链。
2. **对 Prompt 做规范化去重。** 去掉 `const PROMPT =`、字典键和值引号等源码包装后再比较正文，避免把“清洗后的同一条 Prompt”统计为新增。
3. **优先补齐关系分析能力。** 对含局部语法错误的 Python 使用容错解析或分段 AST；为 JavaScript/TypeScript 增加调用、参数和字符串引用关系。只有关系建立后，LLM 找到的候选才能从“看见了”提升为“可归因”。
4. **采用条件式 LLM。** 当确定性分析已经形成完整调用关系时，LLM 主要用于解释和代码观察；当 AST/反编译关系不完整时，再让 LLM承担候选发现。这样能降低成本和重复结果。
5. **保留现有本地验证与人工复核门禁。** 本次结果证明“原文校验 + 关系资格 + 语义复核”三层门禁不能去掉，尤其不能用 LLM 返回的候选条数直接代表准确率。
